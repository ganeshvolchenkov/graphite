What the product is

Graphite breaks trading strategies before the market does. A quant pastes their strategy code and describes a market catastrophe in plain English — "ECB emergency rate hike, EUR/USD spread widens from 0.8 to 65 pips in 300ms, bid-side depth evaporates 94%, then a 450ms feed freeze". The system turns that sentence into a real, executable simulation, runs their actual Python against it tick by tick, and shows the exact moment their code dies.

Then it explains why, rewrites the code to survive, and re-runs it to prove the fix worked. The buyer is a prop desk or quant fund — the tone is professional trading software, not consumer SaaS.

Three AI jobs, each with visible evidence

1 · Comprehension
A reasoning model turns an institutional prompt into a structured market script, and reports which phrases it understood and what it did with each one — quote by quote.
2 · Code adaptation
A code model reads arbitrary strategy source — Zipline class, Backtrader next(), bare signal function — and writes the glue so it runs unmodified.
3 · Repair
After the failure, a model explains it and rewrites the code with the missing guards, which is then re-run for a before/after.

The system deliberately does not fix the user's bugs. If their code divides by zero when the book empties, it still divides by zero — that failure is the product's output. Treat a crash as the headline result, not an error state to apologise for.

The six stages

01

Scenario — plain English to numbers

POST /api/scenarios/interpret
  • A requirements table. One row per demand found: the literal quote from the prompt, a status pill (modelled / approximated / unsupported), what it mappedTo, and a note. The most important panel in the app — it proves the model read the prompt rather than pattern-matched it. Never truncate the quotes.
  • A coverage number (coveragePct). Label it "self-assessed" — it is the model's own judgement, and saying so is more credible than hiding it.
  • An event timeline. script.events[] each have an atMs and a duration — render as a horizontal Gantt, coloured by type.
  • adjustments[] — deterministic corrections the backend applied after the model answered. Shows real engineering behind the model call.
  • Offer 3–4 preset prompts as buttons. Judges will not type a 60-word institutional prompt.
02

Simulation — watch it break

POST /api/simulations · SSE stream

This is the moment that wins or loses the pitch, so it must animate.

  • A live price/equity chart building left to right, ~25ms per tick, ~6s for a full run.
  • Band the background by tick.phase: warmup / shock / recovery / stabilised.
  • A scrolling event log from market_event frames, colour-coded by severity. Real messages: "Spread blew out to 43.7 pips", "Book CROSSED: bid above ask", "Bid side evaporated", "Market data feed frozen".
  • If strategyError is non-null, that is the headline. Vertical rule at the exact tick: "ZeroDivisionError at tick 170 of 220 — your code stopped here."
  • If adapter.adapted is true, show the adapter panel — the interface the AI found, every mapping, and the risks it flagged (e.g. "the strategy ignores bar.halted, so it keeps quoting through the halt").
  • Several seconds pass before the first tick while the AI prepares the strategy. Show a status line saying what is happening, not a bare spinner.
03

Audit — why it failed

POST /api/audits

Verdict (passed/marginal/failed), 0–100 score, headline, narrative, plus strengths[], weaknesses[] and failureModes[] — each with its own severity. Two columns, severity-sorted.

04

Auto-patch — and prove it helped

POST /api/strategies/improve

Returns rewritten code, a summary, and recommendations[] (problem / change / impact). Show a side-by-side diff, then a "re-run patched version" button that sends the new code through stage 2 with variant: "improved".

End on a before/after: two equity curves on one chart, original vs improved, both P&L figures. That comparison is the closing frame of the demo.

05

Run history

GET /api/runs

A compact table of past runs. Low priority — build it last.

06

Model benchmark

GET /api/benchmark

Three models scored on how well they comprehend institutional prompts, across 5 hand-labelled cases — event recall, numeric parameter fidelity, instrument inference, resolution choice. Leaderboard plus a models × cases grid.

Hard requirements

The backend URL must be editable at runtime. A settings input persisted to localStorage under apiBase, with every call routed through one getApiBase() helper. The URL changes on every redeploy, and re-prompting to edit a hardcoded constant wastes real time. Add a status dot polling GET /health every 10s.

  • EventSource will not work — the stream is SSE over POST. Use fetch with a ReadableStream reader; there is a working implementation in backend/API.md.
  • Build against fixtures first. GET /fixtures.json returns real captured responses for every endpoint, including a full 220-tick simulation. Commit it into the project and develop with the backend switched off.
  • Every response is camelCase except /api/benchmark.
  • Percentages are already percentages — drawdownPct: 12.4 means 12.4%.
  • Equity starts at 1,000,000, so absolute P&L numbers look small beside it.

Design direction

Dark, dense, professional — Bloomberg terminal rather than marketing site. Tabular numerals wherever numbers appear, so they do not jitter as they update during the stream. Monospace for code, prompts and quoted phrases. A restrained palette: one neutral surface ramp, one accent for the strategy's series, and a reserved status set never reused for ordinary data.

  • Never a dual-axis chart. Two measures of different scale get two stacked charts sharing an x-axis, never two y-scales.
  • Thin marks, recessive gridlines, direct labels on a few points rather than a number on every point.
  • A legend whenever two or more series are present.
  • Status must never be colour alone — pair every severity colour with an icon or label. Roughly 1 in 12 men has a colour vision deficiency and the judging panel is a small sample.
  • Two different severity scales exist. MarketEvent.severity is info/warn/critical/good; Weakness.severity is low/medium/high/critical. Do not share one colour map.

What not to build

No auth, no signup, no onboarding, no landing page, no pricing, no user accounts. It is a single-screen tool that a judge opens and immediately uses. Every second spent on chrome is a second not spent on the six stages above.
